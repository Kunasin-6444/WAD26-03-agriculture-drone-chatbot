# นโยบายการตรวจงาน

ใช้ร่วมกับ [AGENTS](../AGENTS.md) เป้าหมายคือหาปัญหาที่สำคัญแล้วส่งให้เจ้าของลองได้เร็ว
เอกสารนี้แทน workflow เดิมที่บังคับ full suite/live evaluation ทุกครั้ง

คำสั่งเจ้าของ 2026-10-29: offline tests ใช้จับบั๊กของโค้ด ไม่ใช่คะแนนความแม่นยำของคำตอบจริง เลือกเฉพาะเทสต์ที่คุ้มกับความเสี่ยง และรายงานผลแยกจากการวัดคำตอบกับต้นฉบับ เมื่อเลิกใช้พฤติกรรมให้ลบเทสต์ที่เลิกใช้หรือซ้ำอย่างมีเหตุผล โดยคงตัวตรวจค่าผิด หน่วย เงื่อนไข และแหล่งอ้างอิงที่ยังจำเป็น รวมทั้ง pipeline ที่ยังใช้งาน

| ประเภทงาน | การตรวจเริ่มต้น | ขยายเมื่อใด |
| --- | --- | --- |
| MD/คำอธิบาย | อ่านความสอดคล้อง ตรวจลิงก์ที่แก้และ whitespace | มีคำสั่งหรือ config ที่ต้องยืนยันจากโค้ด |
| UI/formatting เล็กน้อย | เปิดดูหรือ focused offline check ตามจำเป็น | เปลี่ยน request/state flow |
| logic ที่เสี่ยงผิด | focused offline tests ด้วย fixture/stub | มี failure ใหม่หรือกระทบหลาย component |
| retrieval/grounding/citation | ตรวจหลักฐานตัวอย่างและ contract ที่เกี่ยวข้อง offline | ต้องเทียบพฤติกรรมหลายเส้นทางหรือขอวัด live |
| schema/storage/webhook/release | regression ที่ครอบคลุมส่วนที่กระทบ; full suite เมื่อมีเหตุ | เปลี่ยน dependency/สัญญาหลักหรือเตรียม release จริง |
| LLM, embeddings, Vision, Tavily, LINE จริง | ทำเฉพาะขอบเขตที่ผู้ใช้ขอ/อนุญาต | ไม่ขยาย batch หรือรันซ้ำเอง |

## จังหวะการทำงาน

สำหรับstructured query protocol ให้ตรวจสามชั้นแยกกัน: retrievalได้ตาราง/ข้อมูลครบตามscopeหรือไม่;
โมเดลแปลคำถามเป็นtable/column/filter/unit/limitตรงทุกเงื่อนไขหรือไม่; executorคำนวณและอ้างแถวถูกหรือไม่
การป้อนplanเองทดสอบได้เฉพาะbackend ไม่ใช่ความแม่นยำของโมเดลแปลคำถาม
Traceต้องแยกหน้าที่เห็นเพียงschemaจากหน้าที่มีข้อความจริง ไม่รวมเป็นgeneration evidence coverageเดียวกัน
ใช้queryแปลก/หน่วยผิด/ตารางไม่ครบ/ช่วงค่ากำกวม/SQL injectionและข้อสรุปที่quoteตรงแต่อันดับผิดเป็นnegative cases
คงsourceเงื่อนไขพืช/ช่วงใช้/ข้อห้าม/สูตรผสมในprojection ไม่ลดเกณฑ์เพื่อให้schema testsผ่าน
คำถามข้อความ/ขั้นตอนต้องตรวจpayloadว่าคงแถว เลขลำดับ เงื่อนไขและหน้า รวมตารางต่อเนื่อง/ragged/ไม่มีตัวเลข
ตรวจเลขจากquoteจริง ไม่ยอมรับเพราะเลขนั้นอยู่ที่อื่นในหน้า; ตรวจpartial reply/finish_reasonและสถานะrenderer/evaluatorไม่ให้สวมเป็นคำตอบผ่าน

กำหนดพฤติกรรมที่คาดหวัง แก้ปัญหา แล้วตรวจเท่าที่ตอบความเสี่ยงนั้นได้
ใช้ผล focused check ที่ผ่านแล้วต่อได้ ไม่ต้องทวน full suite เว้นแต่การแก้ใหม่ทำให้ผลเดิมไม่น่าใช้
เมื่อ fail ให้อ่านสาเหตุก่อนรันซ้ำ ความล้มเหลวจาก provider ไม่ใช่เหตุให้วน batch ทั้งชุด
ไม่เขียน tests ที่ตรวจเพียงว่า function ถูกเรียก หรือสะท้อน implementation โดยไม่ตรวจพฤติกรรม
งานที่ย้อนกลับง่ายและผลกระทบต่ำไม่จำเป็นต้องเพิ่ม automated test ทุกครั้ง

## สิ่งที่ควรมี coverage เมื่อแก้ส่วนที่เกี่ยวข้อง

- KB พอ: ตอบจาก KB พร้อมชื่อไฟล์/หน้าและเงื่อนไขครบ
- KB บางส่วน: เก็บข้อเท็จจริงเดิม เติม web พร้อมที่มาของแต่ละประเด็น
- Web: ใช้ URL ของหน้าจริง รวม path/query/fragment ไม่แทนด้วย homepage
- ข้อมูลไม่พอ/บริการล่ม: แยกเหตุและไม่แต่งคำตอบหรืออ้างอิง
- ตาราง: ไม่สลับพืช แถว คอลัมน์ ค่า หน่วย และเงื่อนไข
- คำถามใหม่รวมข้อความซ้ำ/พร้อมกันต้องประมวลผลใหม่ ไม่คืนแคชคำตอบ; คิว LINE ยังคงกัน event ID เดิมซ้ำ ส่วน cache ของ retrieval/ingestion ต้องไม่ใช้ข้อมูลผิด revision
- LINE: signature, redelivery/restart, dedup และผลส่งที่ไม่แน่นอน
- Ingestion: provenance, incomplete/degraded และความปลอดภัยของการ publish

รายการนี้เป็น coverage map ไม่ใช่คำสั่งให้รันทุกข้อทุกงาน
ขอบเขตรุ่นส่งล่าสุด 2026-10-26 เลื่อน automatic mixed ออก: ตรวจ KB และ web-only/source routing เป็นหลัก mixed tests เดิมยังเก็บไว้ แต่ไม่ใช้การวัด mixed เป็นเงื่อนไขก่อนส่ง
เก็บ tests เดิมที่ตรวจพฤติกรรมจริง แทนที่ tests ที่ล้าสมัยพร้อมเหตุผล ไม่ลบทิ้งทั้งหมดเพียงเพราะเป็นของเก่า

## Live และการรายงาน

### เกณฑ์รูปแบบ pilot-support-v2 — เจ้าของแก้ความเข้าใจ 2026-10-26

- เกณฑ์นี้แทน v1 ที่ตีความความกระชับเป็นความสั้นเกินไป ต้องตอบพอดีและมีประโยชน์ต่อนักบิน ไม่กำหนด 1–3 ประโยคเป็นเป้าหมายหรือเพดาน
- ประเมินความครบเฉพาะสิ่งที่ถาม คำถามกว้างอาจตอบภาพรวมหรือตัวอย่างโดยบอกขอบเขต ไม่บังคับทั้งตาราง แต่ต้องมีคำอธิบายพอเข้าใจ/ตัดสินใจ/ปฏิบัติได้ ไม่ให้ผ่านเพราะชื่อหัวข้ออยู่ในเรื่องเฉย ๆ
- ถ้าถามจุดตรวจ คำตอบแค่ชื่อชิ้นส่วนยังไม่พอ ต้องมีสิ่งที่ต้องสังเกตตามหลักฐาน ถ้าถามวิธี/อัตราต้องได้ข้อมูลที่นำไปใช้ได้พร้อมเงื่อนไข ไม่บังคับถามเจาะจงซ้ำเพื่อได้คำตอบพื้นฐานที่มีประโยชน์
- ถ้าขอ “ทั้งหมด”, ขั้นตอนครบ หรือถามอัตรา/หน่วย/ความหมายโดยตรง ต้องรักษารายการ ค่ากับหน่วย และเงื่อนไขที่ถามครบ ไม่ใช้ความสั้นลดข้อกำหนดนี้
- ตรวจเพิ่มว่ามีรายละเอียดเกินคำถามหรือคำแนะนำคนละอุปกรณ์/ช่วงงานปนหรือไม่ และคำตอบแรกให้ประเด็นหลักทันทีหรือไม่
- reference ข้อเท็จจริงเดิมยังคงไว้ `must_contain`/expected แบบแจกแจงเก่าบางข้อไม่ใช่เกณฑ์ตัดสินความกระชับใหม่โดยอัตโนมัติ การปรับ rubric ต้องบันทึกเวอร์ชันและคำสั่งเจ้าของ ไม่แก้ expected ให้ตรงคำตอบที่โมเดลเพิ่งสร้าง
- คะแนนรายงานเก่าเป็นผลตามเกณฑ์ในเวลานั้น ห้ามสวมเป็นผล pilot-support-v2 หากเทียบรูปแบบก่อน–หลังต้องใช้ rubric เวอร์ชันเดียวกันทั้งคู่และแยกจากคะแนนเก่า v1 ยังไม่มีผลคำตอบสดก่อนแก้เป็น v2
