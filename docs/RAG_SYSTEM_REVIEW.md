## ข้อสรุป

แนวทาง RAG + CRAG เหมาะกับโจทย์: ใช้เอกสารก่อน ประเมินความเพียงพอ
ค้นเว็บเมื่อข้อมูลไม่พอ และตอบพร้อมแหล่งที่มา แต่ implementation ปัจจุบัน
ยังมีช่องว่างที่ทำให้หยุดค้นเว็บทั้งที่ข้อมูลไม่พอ และแสดงอ้างอิงที่ไม่ได้ตรวจสอบ
จึงยังไม่ควรใช้สถานะ “Production-Ready” หรือ “zero hallucination” เป็นข้อสรุปคุณภาพ

การตรวจครั้งนี้เป็นการทบทวนโค้ด ตรวจฐานข้อมูล และทดสอบแบบ offline
ไม่ได้แก้ production code หรือเรียกบริการ Gemini, KKU GenAI, Tavily และ LINE จริง

## เกณฑ์ยอมรับตามโจทย์

1. ถ้าเอกสารมีคำตอบครบ ต้องตอบจากหลักฐานในเอกสารพร้อมชื่อไฟล์และเลขหน้า
2. ถ้าข้อมูลขาดหรือมีเพียงบางส่วน ต้องค้นเว็บเพิ่มเติมหรือแจ้งส่วนที่ยืนยันไม่ได้
3. คำตอบจากเว็บต้องมาจากเนื้อหาที่ค้น/อ่านได้จริง พร้อม URL ของหลักฐาน
4. คำตอบหลายประเด็นต้องไม่ทำข้อมูลส่วนที่เอกสารตอบได้หายไปเมื่อค้นเว็บ
5. อ้างอิงต้องเป็นแหล่งที่มีอยู่ในหลักฐานที่ตัวสร้างคำตอบได้รับ
   และต้องตรวจว่าข้อความที่ตอบมีหลักฐานสนับสนุน ไม่ใช่ตรวจแค่มีคำว่า “อ้างอิง”
6. หากหลักฐานไม่พอทั้งสองทาง ต้องแจ้งว่าไม่สามารถยืนยันได้โดยไม่เดา
7. การจัดการปัญหาบริการภายนอกต้องไม่ทำให้ระบบอ้างว่าได้ค้นหรือยืนยันแล้ว

## สิ่งที่ตรวจพบว่าเป็นพื้นฐานที่ดี

- `app/services/ai_service.py` เรียก CRAG pipeline จริง ไม่ใช่ LLM ตอบจากความรู้ล้วน
- มี retrieval, relevance grader, Tavily search, grounded generator และ abstain path แยกกัน
- Knowledge Unit และ chunk เก็บชื่อไฟล์ เลขหน้า และประเภทแหล่งข้อมูล
- ฐาน `chroma_db/drone_knowledge` มี 912 chunks จาก 7 เอกสาร
  (UAV06: 126, UAV07: 107, UAV08: 172, UAV09: 103, UAV10: 215,
  UAV11: 77, UAV12: 112) ไม่มี chunk ที่ขาดชื่อไฟล์หรือเลขหน้า
- UAV07 หน้า 12 มี 7 chunks และพบข้อความ `500` กับ `2.8`
  การตรวจนี้ยืนยันว่าหลักฐานอยู่ในฐานข้อมูล ไม่ได้ยืนยันคุณภาพ semantic retrieval ของคำถามใหม่
- เทสต์ offline ที่เกี่ยวข้องผ่าน 54/54

## ประเด็นที่ต้องแก้ก่อนยืนยันว่าครบโจทย์

### 1. CAAT มี URL แต่ไม่ได้อ่านหลักฐานจากเว็บจริง — สูง

ตำแหน่ง: `app/rag/web_fallback.py:103` และ `:247`

เส้นทาง CAAT สร้าง `caat_content` จากข้อความที่เขียนไว้ในโค้ด แล้วคืนผล
ที่มี `is_trusted=True` โดยไม่เรียก search หรือ extract ส่วน prompt ยังเติม
ข้อเท็จจริงเกี่ยวกับกฎหมายซ้ำอีกครั้ง จึงไม่ใช่การอ่านข้อมูลปัจจุบันจาก CAAT
การมี URL ท้ายคำตอบเพียงอย่างเดียวไม่พิสูจน์ว่าข้อมูลมาจาก URL นั้น

ทดสอบซ้ำ: ส่ง mocked Tavily client แล้วพบว่าไม่มีการเรียก search/extract

แนวทางแก้: อ่านแหล่งที่กำหนดจริง เก็บ URL และเวลาที่ดึงข้อมูล หากอ่านไม่ได้
ให้แจ้งว่ายังยืนยันไม่ได้พร้อมลิงก์สำหรับตรวจสอบ ห้ามนำข้อความกฎหมายในโค้ดมาแทนหลักฐาน
รายงานนี้ไม่ได้ตรวจหรือรับรองความถูกต้องของรายละเอียดกฎหมายในข้อความดังกล่าว

### 2. AMBIGUOUS และคำตอบว่าไม่มีข้อมูลบางรูปแบบหยุดก่อนค้นเว็บ — สูง

ตำแหน่ง: `app/rag/crag_service.py:211` และ `:224`

ระบบยอมให้ `AMBIGUOUS` เข้าทางตอบจากเอกสาร แม้ `is_relevant=False`
และตรวจ abstain จากข้อความภาษาไทยเฉพาะรูปแบบ เช่น ถ้าตอบว่า
“ไม่มีข้อมูลราคาของหัวฉีด” พร้อมอ้างอิง ระบบกลับคืน `knowledge_base` โดยไม่ค้นเว็บ

ทดสอบซ้ำ: ทั้งกรณีหลักฐานบางส่วนและกรณีปฏิเสธคำตอบรูปแบบข้างต้นเรียก web search 0 ครั้ง

แนวทางแก้: ให้ grader/generator คืนสถานะที่มีโครงสร้าง เช่น
`sufficient`, `partial`, `insufficient`, `abstain` และระบุประเด็นที่ขาด
ค้นเว็บสำหรับส่วนที่ขาด แล้วรวมหลักฐานที่ตอบได้จากเอกสารไว้ด้วย
หากคำถามกำกวมจนไม่รู้ว่าจะค้นอะไร ให้ขอรายละเอียดแทนการเดา

### 3. อ้างอิงยังเป็นการจัดรูปแบบ ไม่ใช่การตรวจหลักฐาน — สูง

ตำแหน่ง: `app/rag/rag_service.py:200`, `app/rag/web_fallback.py:299`
และ `app/rag/format_utils.py:211`

หากโมเดลไม่ระบุอ้างอิง ระบบเลือกไฟล์/หน้าแรกหรือเว็บแรกมาเติมเอง
หากโมเดลระบุชื่อ PDF หรือ URL ที่ไม่ได้อยู่ใน context ก็ยังไม่มีตัวตรวจว่ามีจริง

ทดสอบซ้ำ: context มี `UAV07.pdf` หน้า 12 แต่ mocked LLM อ้าง
`invented.pdf` หน้า 999 และระบบคืนอ้างอิงดังกล่าวตามเดิม
การทดสอบนี้แสดงว่าไม่มีการปฏิเสธอ้างอิงผิด ไม่ได้วัดอัตราที่โมเดลจริงจะสร้างอ้างอิงผิด

แนวทางแก้: กำหนด evidence ID ให้แต่ละแหล่ง ให้โมเดลระบุ ID ที่ใช้
ตรวจ ID กับหลักฐานที่ได้รับ แล้วประกอบชื่อไฟล์/หน้า/URL ฝั่ง backend
เพิ่มการประเมินว่าข้อความที่ตอบตรงกับแหล่งนั้นจริง โดยเฉพาะตัวเลขและคำถามหลายประเด็น

### 4. ตัวประเมินกับตัวตอบเห็นหลักฐานคนละส่วน — สูง

ตำแหน่ง: `app/rag/crag_grader.py:112` และ `app/rag/rag_service.py:163`

grader ตัดที่ 4,500 ตัวอักษร แต่ generator ตัดที่ 4,200 ตัวอักษร
จึงมีโอกาสประเมินว่าพอจากข้อความที่ตัวตอบไม่ได้เห็น อีกทั้งการตัดกลาง string
อาจแยกแถวตารางหรือเนื้อหาจาก metadata และทิ้งหลักฐานของประเด็นท้ายคำถาม

ทดสอบซ้ำ: จับ prompt ของทั้งสองฝั่งแล้วพบปริมาณหลักฐานไม่เท่ากัน

แนวทางแก้: จัด context เพียงครั้งเดียวก่อน grading ใช้ evidence blocks เดียวกันทั้งสองฝั่ง
ควบคุม budget โดยรักษาหน่วยหลักฐานที่สมบูรณ์และครอบคลุมประเด็นคำถาม

### 5. หน้าที่มีตารางทำให้ข้อความประกอบถูกทิ้ง — สูง

ตำแหน่ง: `app/rag/slide_retriever.py:255` และ `:267`

เมื่อพบ table หรือ diagram บนหน้า ระบบไม่รวม text/image จากหน้าเดียวกัน
แม้ text นั้นเป็น chunk ที่ retrieval พบ อาจทำเงื่อนไขการทดลอง ข้อจำกัด
หรือข้อควรระวังที่จำเป็นต่อการตีความตัวเลขหายไป

ทดสอบซ้ำ: mock หน้าเดียวกันที่มี `TEXT_EVIDENCE` กับ `TABLE_EVIDENCE`
ผล context เหลือเฉพาะตาราง

แนวทางแก้: เก็บหลักฐานข้อความที่เกี่ยวข้องร่วมกับตาราง ลดเฉพาะข้อความซ้ำ
อย่าตัดข้อความทั้งหมดเพียงเพราะหน้าเดียวกันมีตาราง

### 6. การจัดเว็บเป็นแหล่งเชื่อถือได้ตรวจผิดส่วนของ URL — สูง

ตำแหน่ง: `app/rag/web_fallback.py:58`

ใช้ substring กับ URL ทั้งเส้น ทำให้
`https://attacker.example/caat.or.th` และ
`https://caat.or.th.attacker.example/` ถูกจัดเป็นแหล่งที่เชื่อถือได้
ทั้งที่ hostname ไม่ใช่ CAAT

ทดสอบซ้ำ: ทั้งสอง URL คืน `True`

แนวทางแก้: ใช้ `urlparse(url).hostname` แล้วตรวจชื่อโดเมนตรงตัว
หรือ subdomain ด้วยขอบเขตจุด รวมทั้งอย่าถือว่า `.or.th` ทุกเว็บเป็นแหล่งทางการ
การเชื่อถือโดเมนไม่ได้แทนการตรวจความเกี่ยวข้องและความเพียงพอของเนื้อหา

### 7. Retrieval ล้มเหลวแล้วไม่ไปต่อทางเว็บ — กลาง

ตำแหน่ง: `app/rag/crag_service.py:150` และ `app/rag/embedding.py`

ไม่มีการรับข้อผิดพลาดรอบ retrieval ถ้า embedding หรือ Chroma ล้มเหลว
pipeline จะโยน exception ไป webhook ซึ่งตอบเพียงข้อความระบบมีปัญหา
การ retry embedding อาจใช้เวลาหลายนาทีเมื่อเจอ quota limit

ทดสอบซ้ำ: mock retrieval ให้โยน exception แล้ว pipeline ไม่เรียก web fallback

แนวทางแก้: แยก “ค้นแล้วไม่มีข้อมูล” กับ “ค้นไม่ได้เพราะบริการล้มเหลว”
กำหนด timeout/retry budget และใช้เว็บได้เมื่อเหมาะสม พร้อมเก็บสถานะสำหรับตรวจสอบ

## ข้อสังเกตเพิ่มเติมจากโค้ด

- Hybrid route ใน `crag_service.py:109` ตรวจจากคำสำคัญจำกัดและยอมรับเพียงว่า
  KB context กับ web results ไม่ว่าง โดยไม่ตรวจความเพียงพอของทั้งสองฝั่ง
  prompt ของ `generate_hybrid_grounded_answer` ระบุหัวฉีดและราคาน้ำมันตายตัว
  จึงไม่ครอบคลุมคำถามเอกสาร+เว็บทั่วไป และอาจเปลี่ยนหัวข้อคำถาม
- `query_normalizer.py` เติม “Ultra-Coarse พัดแดง” ให้คำว่า “คุมดิน”
  ซึ่งเป็นการเติมเนื้อหาคำตอบมากกว่าการแก้คำพิมพ์ผิด และ normalization ไม่เป็น idempotent
  ขณะที่ CRAG กับ slide retriever ต่างก็เรียก normalization ทำให้เกิดคำขยายซ้ำ
- `slide_retriever.py` เริ่มจาก dense top-50 แล้วให้ lexical score เฉพาะในชุดนั้น
  ไม่ใช่ lexical retrieval ทั้ง corpus และฟังก์ชันที่เรียก BM25 ไม่ได้คำนวณ IDF
  ควรอธิบายชื่อขั้นตอนให้ตรงกับสิ่งที่ทำ และวัด baseline ก่อนเพิ่มความซับซ้อน
- `scripts/ingest_all_data.py:14` อ่าน PDF ทุกไฟล์ และ `ingest_pdf` ไม่มี guard
  สำหรับไฟล์ยกเว้นตาม R1 ปัจจุบันฐานไม่มี UAV01/UA03 แต่การ ingest ครั้งต่อไป
  อาจนำเข้าหากไฟล์เหล่านั้นอยู่ใน data เอกสารสถานะจึงอ้างว่าป้องกันไว้มากกว่าที่โค้ดบังคับจริง
- `call_llm` ใช้ `message.reasoning` แทน final content เมื่อ content ว่าง
  การตัดด้วย regex ไม่รับประกันว่าจะได้คำตอบสุดท้าย ควรใช้ final content ที่ครบถ้วน
  หรือ fallback โมเดล และตรวจ finish reason เมื่อข้อความถูกตัด
- `scripts/evaluate_benchmark.py` ตรวจ routing/คำสำคัญ/การมีอ้างอิง
  ยังไม่ตรวจว่าทุกข้อเท็จจริงและอ้างอิงได้รับการสนับสนุนจากหลักฐานจริง
  ผล benchmark เดิมจึงไม่พิสูจน์ว่าไม่มี hallucination

ควรแยก test database และเพิ่มวิธีเปิด live tests อย่างชัดเจนก่อนรันทั้งชุด
จึงยังไม่รับรอง full-suite pass, คุณภาพการตอบจริง, ความสดของเว็บ หรือ latency

## ลำดับงานที่แนะนำ

1. ใช้หลักฐาน CAAT ที่อ่านได้จริง ตรวจ hostname และตรวจอ้างอิงกับ evidence IDs
2. เก็บ text ที่เกี่ยวข้องร่วมกับตาราง และจัด context เดียวกันให้ grader/generator
3. ใช้ structured sufficiency/abstention ตัดสิน fallback รวมถึงข้อมูลที่ขาดบางส่วน
4. ทำ hybrid generation ให้ตอบตามคำถามทั่วไปและตรวจทั้งสองแหล่ง
5. แยกฐานทดสอบ เพิ่ม regression tests จาก audit และรัน live Thai retrieval/end-to-end
   เพื่อวัดความครบของคำตอบและความถูกต้องของอ้างอิงก่อนประกาศพร้อมใช้งาน
