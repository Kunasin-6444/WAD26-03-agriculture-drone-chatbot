# Oral Defense Q&A

รวบรวมคำถามที่อาจารย์หรือคณะกรรมการสอบอาจจะถามเกี่ยวกับสถาปัตยกรรมและการตัดสินใจในโปรเจกต์ พร้อมแนวทางการตอบ

## หมวดที่ 1: ภาพรวมระบบและวัตถุประสงค์ (System Overview & Goals)

### Q1: ทำไมถึงต้องทำ Chatbot ตัวนี้ขึ้นมา แก้ปัญหาอะไร และใครคือผู้ใช้งาน?
**แนวทางการตอบ**:
- เกษตรกรและผู้รับจ้างบินโดรนเพื่อการเกษตรในไทย มักประสบปัญหาเรื่องการสืบค้นข้อมูลเชิงเทคนิค เช่น การเลือกหัวฉีดที่เหมาะสมกับชนิดสารเคมี อัตราการไหล ความสูง ความเร็วในการบิน รวมถึงข้อกำหนดทางกฎหมาย ซึ่งข้อมูลเหล่านี้กระจัดกระจายอยู่ในคู่มือ PDF หลายร้อยหน้าและเอกสารราชการ
- ปัญหาของการใช้ ChatGPT ทั่วไปคือ มักเกิด "Hallucination" (การคิดคำตอบเอง) หรืออ้างอิงข้อมูลโดรนทั่วไปที่ไม่ตรงกับหลักปฏิบัติทางการเกษตรของไทย ซึ่งอาจทำให้พืชผลเสียหายหรือละเมิดกฎหมายการบิน
- ระบบนี้จึงสร้างเป็น LINE Chatbot ที่ทำงานบนสถาปัตยกรรม RAG และ CRAG โดยบังคับให้ตอบจากเอกสารทางการเกษตรที่ตรวจสอบแล้ว พร้อมบอกเลขหน้าอ้างอิง และมีระบบปฏิเสธการตอบ (Abstain) เมื่อไม่มีข้อมูลยืนยัน เพื่อความปลอดภัยสูงสุด

### Q2: Flow การทำงานเมื่อผู้ใช้พิมพ์คำถามผ่าน LINE เข้ามา ระบบทำอะไรบ้างตั้งแต่ต้นจนจบ?
**แนวทางการตอบ**:
1. ผู้ใช้พิมพ์คำถามผ่านแอป LINE บนมือถือ
2. เซิร์ฟเวอร์ LINE ยิง Webhook HTTP POST เข้ามาที่ `/webhook` ของ FastAPI backend
3. Backend ตรวจสอบลายเซ็น `x-line-signature` เพื่อยืนยันว่า Request มาจาก LINE จริง
4. ดึงข้อความคำถามส่งเข้าสู่ระบบประมวลผล RAG/CRAG
5. เมื่อได้ข้อความคำตอบพร้อมแหล่งอ้างอิง ระบบจะเรียกใช้ LINE Messaging API (`reply_text`) ส่งข้อความกลับไปหาผู้ใช้ผ่าน `replyToken` ภายในรอบเดียว

### Q3: ในโค้ด LINE Service ทำไมถึงตัดความยาวข้อความไว้ที่ 4,950 ตัวอักษร ทั้งที่ LINE อนุญาตได้ถึง 5,000 ตัวอักษร?
**แนวทางการตอบ**:
- เพื่อเป็น **Safety Margin (Headroom)** ป้องกันข้อผิดพลาด HTTP 400 Bad Request
- LINE นับจำนวนตัวอักษรแบบ Unicode code points (UTF-16) ซึ่งในภาษาไทยหรือข้อความที่มี Emoji บางตัวอักษรอาจถูกนับเป็น Surrogate pairs (หลาย byte/code point) อีกทั้งในการ Serialize ข้อมูลเป็น JSON ส่งผ่านเครือข่าย อาจมี Escape characters (เช่น `\n`, `\"`) ที่ทำให้ความยาวเพิ่มขึ้น
- การตัดไว้ที่ 4,950 ตัวอักษร (เผื่อไว้ 50 ตัวอักษร) ช่วยรับประกัน 100% ว่าข้อความจะไม่มีทางเกินขีดจำกัด 5,000 ตัวอักษรของ LINE อย่างแน่นอน

### Q4: ทำไมโปรเจกต์นี้ถึงไม่เลือกใช้ LangChain หรือ LangGraph ในการพัฒนา RAG?
**แนวทางการตอบ**:
1. **Transparency & Controllability**: Plain Python ทำให้เราเห็นลำดับการทำงาน (Data Flow) ทั้งหมดชัดเจน ไม่มี Abstraction หรือ Hidden Prompt มารบกวน สามารถกำหนด Prompt กฎหมายการบิน และการอ้างอิงแหล่งที่มาได้แม่นยำ 100%
2. **Easy Debugging & Profiling**: เมื่อเกิดปัญหาความล่าช้า (Latency) หรือโมเดลตอบผิด เราสามารถวัดเวลาและวาง breakpoint ตรวจสอบได้ทีละบรรทัด โดยไม่ต้องไล่ผ่าน Framework ซ้อนกันหลายชั้น
3. **Lightweight**: ไม่ต้องแบกรับ Dependency ขนาดใหญ่ที่อาจเกิดปัญหาเวอร์ชันขัดแย้งกันในอนาคต

### Q5: ทำไมต้องแยก Ingestion Pipeline ออกจาก Query Pipeline ให้เด็ดขาดจากกัน?
**แนวทางการตอบ**:
- Ingestion Pipeline เป็นงานประเภท **Batch / Heavy Processing** (อ่านไฟล์ PDF, สกัดรูปภาพ, ทำ OCR, ยิง Gemini Vision, สร้าง Chunks และคำนวณ Embedding 3072 มิติ) ซึ่งใช้เวลาประมวลผลเป็นนาทีและกินทรัพยากรสูง จึงต้องทำแบบ Offline ล่วงหน้าเพียงครั้งเดียวแล้วบันทึกลง Persistent ChromaDB
- ส่วน Query Pipeline เป็นงานประเภท **Real-time / Interactive** ที่ผู้ใช้กำลังรอคำตอบผ่าน LINE ต้องทำงานให้เร็วที่สุด (ไม่เกินไม่กี่วินาที) ดังนั้นระบบจะไม่ไปเปิดไฟล์ PDF ใหม่ แต่จะแปลงคำถามเป็นเวกเตอร์แล้วค้นหาบน ChromaDB ได้ทันที

### Q6: ทำไมถึงต้องแปลงตารางใน PDF เป็น Pipe-separated Text (`|`) และมีวิธีป้องกันไม่ให้ข้อความในตารางถูกดึงซ้ำซ้อนอย่างไร?
**แนวทางการตอบ**:
- ตารางสเปกหัวฉีดมีความสัมพันธ์ระหว่างคอลัมน์ (เช่น ชนิดหัวฉีด อัตราการไหล ความดัน) การแปลงเป็น Pipe-separated text ช่วยรักษาโครงสร้างแถว-คอลัมน์ให้ Embedding Model และ LLM เข้าใจความสัมพันธ์ของข้อมูลได้อย่างสมบูรณ์
- เพื่อไม่ให้ข้อความในตารางซ้ำกับข้อความปกติ ระบบจะใช้ `page.find_tables()` เพื่อหาพิกัด Bounding Box ของตารางก่อน และตอนดึงข้อความทั้งหน้า จะกรองบล็อกข้อความ (`Rect`) ที่ตกอยู่ในกรอบตารางออก ทำให้ไม่มีข้อความซ้ำซ้อนในระบบ

### Q7: ทำไมโปรเจกต์ถึงยกเว้นไฟล์ UAV01 Air Law และ UA03 AIR SPACE จากการ Ingest เข้าฐานข้อมูล PDF ปกติ?
**แนวทางการตอบ**:
- เป็นข้อกำหนดตาม **Rule R1** ของโครงการ เนื่องจากกฎหมายการบินโดรนและข้อกำหนดเขตพื้นที่การบินของไทยมีการปรับปรุงแก้ไขจากสำนักงานการบินพลเรือนแห่งประเทศไทย (CAAT) อยู่สม่ำเสมอ เอกสาร PDF เก่าอาจล้าสมัยและก่อให้เกิดอันตรายทางกฎหมายต่อเกษตรกร
- ระบบจึงกำหนดให้เมื่อมีคำถามด้านกฎหมายหรือเขตพื้นที่การบิน ระบบจะทำการ Fallback ไปยังแหล่งข้อมูลทางการสดใหม่จาก **CAAT UAS Portal** (`https://uasportal.caat.or.th/infographic`) โดยตรงแทน

### Q8: ทำไมระบบถึงไม่ใช้ Vision Model วิเคราะห์เอกสาร PDF ทุกหน้า และมีวิธีเลือกอย่างไรว่าหน้าไหนควรใช้?
**แนวทางการตอบ**:
- การส่งทุกหน้าไป Vision API จะทำให้สิ้นเปลืองเวลาอย่างมาก และติดปัญหาขีดจำกัดโควตา **HTTP 429 Resource Exhausted** ทำให้ Ingestion ล่ม
- เราจึงสร้าง **Selective Vision Heuristics** ใน `app/ingestion/vision_extractor.py` (ฟังก์ชัน `should_use_vision()`) โดยวิเคราะห์ว่าหากหน้าใดเป็นตัวหนังสือปกติ จะใช้ PyMuPDF สกัดข้อความทันที (เร็วกว่า 100 เท่า, โควตา 0) และจะเลือกส่งเข้า Gemini Vision เฉพาะหน้าที่มีสัญญาณภาพเด่นชัด เช่น มีรูปภาพขนาดใหญ่ (>150x150), มี Vector Drawing ซับซ้อนเกิน 10 รูป, ข้อความน้อยแต่มีรูปภาพ หรือพบปัญหาฟอนต์เสียหาย (Corrupted Font)

### Q9: ในระบบนี้มีการทำ Caching ตรงไหนบ้าง และแต่ละจุดแก้ปัญหาอะไร?
**แนวทางการตอบ**:
- ระบบมี Caching 2 ระดับตามประเภทของงาน:
  1. **Disk Cache ใน Ingestion (`cache/vision/`)**: บันทึกผลลัพธ์ JSON ของ Vision API ลงฮาร์ดดิสก์ ช่วยให้ตอนพัฒนาหรือทดลองปรับแต่งระบบ Chunking สามารถ Re-ingest ได้ทันทีโดยไม่ต้องเสียโควตาและเวลาเรียก Gemini Vision ซ้ำ
  2. **In-Memory Model Cache ใน RAG Service (`_EXHAUSTED_MODELS`)**: จดจำรายชื่อ LLM บน KKU GenAI ที่โควตารายวันเต็ม (HTTP 401) ไว้ใน RAM ชั่วคราว เพื่อข้ามไปเรียกโมเดลตัวอื่นที่พร้อมใช้งานทันที ทำให้ระบบไม่ต้องเสียเวลารอ Retry ซ้ำทุกรอบคำถามของผู้ใช้

### Q10: ทำไมถึงต้องมีโมเดล `KnowledgeUnit` คั่นกลางระหว่างการสกัด PDF กับการทำ Chunking?
**แนวทางการตอบ**:
- เป็นการนำหลักการ **Data Contract (Single Source of Truth / Intermediate Representation)** มาใช้ในเชิงสถาปัตยกรรม
- เนื่องจากผลลัพธ์ที่ได้จาก Text Extractor, Table Extractor และ Vision Extractor มีโครงสร้างข้อมูลที่ต่างกัน หากส่งไปยังโมดูล Chunking โดยตรงจะทำให้โค้ดผูกติดกันแน่น (Tight Coupling) และอาจทำข้อมูลแหล่งที่มาสูญหาย
- การแปลงข้อมูลทุกประเภทให้อยู่ในรูป `KnowledgeUnit` ช่วยรับประกันว่าข้อมูลทุกชิ้นจะถูกเก็บบันทึก `source_file` และ `page_number` ไว้เสมอ ทำให้สามารถอ้างอิงแหล่งที่มากลับไปยังหน้าคู่มือต้นทางได้ 100% ตอบโจทย์ข้อกำหนด Traceability อย่างสมบูรณ์

### Q11: ระบบกำหนดขนาด Chunk Size และ Overlap เท่าใด และมีเทคนิคพิเศษสำหรับข้อมูลตาราง (Table) อย่างไร?
**แนวทางการตอบ**:
- ระบบกำหนด Baseline ไว้ที่ `chunk_size = 800` ตัวอักษร และ `chunk_overlap = 120` ตัวอักษร เพื่อรักษาความต่อเนื่องของประโยคบริเวณรอยต่อ (Sliding Window)
- แต่มีข้อยกเว้นพิเศษที่เรียกว่า **Structured Unit Protection**: หากเป็นข้อมูลประเภท `table`, `diagram`, หรือ `chart` ที่มีความยาวไม่เกิน 1,200 ตัวอักษร ระบบจะไม่ตัดแบ่ง แต่จะเก็บไว้ทั้งผืนเป็น 1 Chunk ทันที เพื่อป้องกันไม่ให้ข้อมูลสเปก (เช่น ขนาดละออง, อัตราการไหล) ขาดออกจากหัวตาราง (Header) ซึ่งจะทำให้เสียความหมาย

### Q12: ในคลาส `Chunk` ทำไมต้องมีทั้ง Attribute เดี่ยว (เช่น `page_number: int`) และมี `metadata: dict` ซ้ำอีกชั้นหนึ่ง? สิ่งไหนถูกนำไป Embed?
**แนวทางการตอบ**:
- มี 2 ชั้นเพื่อประโยชน์คนละด้าน:
  1. **Python Type Safety & Autocomplete**: การมี Attribute แบบ Typed (เช่น `chunk.page_number`) ช่วยให้ Developer เขียนโค้ดใน Python ได้สะดวก มี Type checking ป้องกันการสะกดชื่อฟิลด์ผิด
  2. **ChromaDB API Contract**: เมธอด `collection.upsert()` ของ ChromaDB รับ Metadata ในรูป `list[dict]` การเตรียม `chunk.metadata` ไว้ล่วงหน้าทำให้ส่งเข้า ChromaDB ได้โดยตรงทันที
- **สิ่งที่ถูกนำไป Embed**: มีเพียงข้อความใน **`chunk.content`** เท่านั้น ส่วน Metadata ทั้งหมดไม่ได้ถูกนำไปแปลงเป็นเวกเตอร์ แต่จะถูกบันทึกเป็น Attribute กำกับอยู่ข้างเวกเตอร์ใน ChromaDB เพื่อส่งคืนกลับมาตอน Search สำเร็จ

### Q13: Embedding Model ในโปรเจกต์นี้ทำงานอย่างไร และทำไมถึงค้นหาข้อมูลเจอแม้ผู้ใช้จะพิมพ์คำไม่ตรงกับในคู่มือ PDF?
**แนวทางการตอบ**:
- เราใช้โมเดล `gemini-embedding-2` ซึ่งแปลงข้อความเป็นเวกเตอร์ตัวเลขขนาด 3,072 มิติ
- การค้นหาไม่ได้ใช้หลักการจับคู่คำแบบตรงตัว (Exact Keyword Match) แต่ใช้ **Semantic Similarity** ในพื้นที่เวกเตอร์หลายมิติ
- คำหรือประโยคที่มีความหมายเชิงบริบทใกล้เคียงกัน เช่น "nozzle สีส้ม" กับ "หัวฉีดส้ม" หรือ "ความสูงการบิน" กับ "บินสูงกี่เมตร" จะถูกคำนวณเวกเตอร์ให้อยู่ในทิศทางและตำแหน่งที่ใกล้เคียงกัน (ผ่านการวัดค่า Cosine Distance) ทำให้ ChromaDB สามารถดึงข้อมูลที่เกี่ยวข้องออกมาตอบคำถามได้อย่างแม่นยำแม้ผู้ใช้จะใช้คำศัพท์คนละคำกัน

### Q14: ตอนที่ค้นหาข้อมูลใน ChromaDB ได้ผลลัพธ์ออกมาเป็นเวกเตอร์ใช่หรือไม่ แล้วระบบส่งต่อไปให้ LLM ได้อย่างไร LLM อ่านเวกเตอร์ออกหรือไม่?
**แนวทางการตอบ**:
- **ความจริงคือ**: สิ่งที่ส่งไปให้ LLM ไม่ใช่ตัวเลขเวกเตอร์ แต่เป็น **"ข้อความตัวหนังสือภาษาไทยจริง (Thai Text)"**
- ตอนที่บันทึกข้อมูลเข้า ChromaDB เราส่งทั้งข้อความดิบ (`documents`) และเวกเตอร์ (`embeddings`) เก็บไว้คู่กัน
- เมื่อทำการ `collection.query()` ChromaDB จะใช้เวกเตอร์ในการคำนวณหาระยะห่าง (Cosine Distance) ในเชิงคณิตศาสตร์ แต่ผลลัพธ์ที่มัน Return กลับมาให้เราคือ Dictionary ที่มีคีย์ `documents` (ข้อความชิ้นที่ใกล้ที่สุด) และ `metadatas` (ชื่อไฟล์และเลขหน้า)
- ระบบของเราจะนำข้อความภาษาไทยและเลขหน้าเหล่านี้ มาจัดรูปแบบเป็นบริบท (Context) ใส่ใน Prompt ส่งให้ LLM (KKU GenAI) อ่านเพื่อตอบคำถาม ดังนั้น LLM ไม่ต้องอ่านเวกเตอร์เลย เพราะมันอ่านตัวหนังสือภาษาไทยที่ Chroma คืนค่ามาให้ครับ
