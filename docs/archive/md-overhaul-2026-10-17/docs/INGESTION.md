# การนำเอกสารเข้า Knowledge Base (ingestion v2)

> ผลล่าสุด: [RELEASE_READINESS_2026-10-17.md](../../../RELEASE_READINESS_2026-10-17.md)
> ทดลอง API และ publish เอกสารใหม่จริงแล้ว มีการซ่อมเส้นขอบตารางที่เรียก Vision เกินจำเป็น
> และปฏิเสธ Vision ที่วนคำซ้ำ หน้า 38 ของไฟล์การลงทุนยังอ่านภาพไม่สำเร็จหลัง 3 attempts
> จึงยังเป็น incomplete แม้ native text ถูกเก็บแล้ว รายการ “ยังไม่ได้ตรวจกับ API จริง”
> ด้านล่างเป็นสถานะก่อนรอบส่งมอบ ไม่ใช่สถานะล่าสุด

คำสั่งหลักคือ `python -m scripts.ingest` ใช้สำหรับ PDF ที่มีข้อความและตารางในไฟล์ (เช่นเอกสารจาก Word/Google Docs) และสไลด์ที่ต้องอ่านด้วยภาพ ตัวเก่า (`scripts.ingest_pdf`, `scripts.ingest_all_data`) ยังอยู่สำหรับโหมด `direct` แต่ **ไม่ควรใช้ `ingest_all_data` กับ index ปัจจุบัน** เพราะจะ ingest ซ้ำทุกไฟล์ด้วยวิธีเก่า

## ขั้นตอนใช้งาน

```powershell
# 1. วางไฟล์ใน data/  (ตั้งชื่อ "UAV13 ชื่อเรื่อง.pdf" เพื่อให้ document id เป็น UAV13)
# 2. ดูแผนและค่าใช้จ่ายก่อน — ออฟไลน์ ไม่เรียก API ไม่แตะ index
.venv/Scripts/python.exe -B -m scripts.ingest --dry-run

# 3. ทดลองไฟล์เดียว 1-2 หน้าก่อน (ครั้งแรกบน provider จริงควรทำขั้นนี้)
.venv/Scripts/python.exe -B -m scripts.ingest "data/UAV13 ....pdf" --pages 1-2

# 4. ingest ทั้งหมดที่ยังใหม่หรือเปลี่ยน
.venv/Scripts/python.exe -B -m scripts.ingest

# 5. ตรวจความสมบูรณ์ (ออฟไลน์)
.venv/Scripts/python.exe -B -m scripts.verify_ingestion
```

ตัวเลือก: `--vision auto|always|never` (ค่าเริ่มต้น auto), `--workers N` (vision พร้อมกัน ค่าเริ่มต้น 3), `--force` (แทนที่แม้ไฟล์ไม่เปลี่ยน/เป็นของ pipeline เก่า), `--doc-id ID` (ไฟล์เดียว), `--report-dir`

รายงานต่อไฟล์อยู่ที่ `cache/ingestion/<id>.<sha8>.report.json` มีหน้าที่ใช้ vision พร้อมเหตุผล, หน้าว่าง, ตารางที่ต่อข้ามหน้า, เวลาแต่ละขั้น exit code เป็น 1 เมื่อมีไฟล์ไม่สมบูรณ์หรือล้มเหลว

## สถานะของไฟล์ใน index

| สถานะ | ความหมาย | พฤติกรรมเริ่มต้น |
| --- | --- | --- |
| new | ยังไม่มีใน index | ingest |
| up_to_date | sha256 และเวอร์ชัน pipeline ตรงกัน | ข้าม ไม่เรียก API |
| stale | ไฟล์หรือเวอร์ชัน pipeline เปลี่ยน | ingest แล้วแทนที่ chunk เดิมทั้งไฟล์ |
| legacy | อยู่ใน index จาก pipeline เก่า (ไม่มี `source_sha256`) | ข้าม ต้อง `--force` ระบุชื่อไฟล์ |

ไฟล์ UAV06–UAV12 ปัจจุบันเป็น legacy จึงไม่ถูกแตะโดยคำสั่งเริ่มต้น

## สิ่งที่เปลี่ยนจากเดิม และเหตุผล (วัดจากข้อมูลจริง)

| ปัญหาเดิม | หลักฐาน | วิธีใหม่ |
| --- | --- | --- |
| ตัด chunk ทุก 800 ตัวอักษรกลางแถวตาราง | ตาราง UAV06 หน้า 18 ถูกตัดเป็น 3 ชิ้น ชิ้น 2–3 ขึ้นต้นกลาง cell และไม่มีหัวตาราง | ตัดตามแถว ทุกชิ้นขึ้นต้นด้วยหัวตาราง ไม่ตัดกลางแถว |
| ตารางข้ามหน้าเสียหัวตาราง | ตัวตรวจ `table_grounding` ถือแถวข้อมูลแรกที่ไม่มีหัวเป็น "หัวตาราง" | ต่อตารางข้ามหน้า สืบทอดหัวตาราง และบันทึก `header_inherited` |
| แถวที่รวมเซลล์ (หัวข้อกลุ่ม) หลุดจากแถวข้อมูล | ตารางสารเคมีมีแถว "กลุ่ม 1: ..." คั่น | เป็นคอลัมน์ `หัวข้อกลุ่ม` ท้ายแถว ค่าเดิมไม่ถูกแก้ |
| ข้อความหน้าเดียวเป็น chunk ก้อนเดียวแล้วตัดตามตัวอักษร | ไม่มีหัวข้อ/ย่อหน้า | อ่านหัวข้อ (ขนาด/ตัวหนา/เลขข้อ) จัดย่อหน้า ต่อบรรทัดภาษาไทยที่ถูกตัดกลางคำ |
| บริบทของ chunk ขาด | chunk ไม่รู้ว่าอยู่หัวข้อใด | ชื่อเอกสาร › หัวข้อ › ชื่อตาราง ถูกใส่ในข้อความที่ **embed** เท่านั้น ข้อความที่เก็บเป็นหลักฐานยังเป็นของ PDF ล้วน (การตรวจ quote ไม่เปลี่ยน) |
| vision ทุกหน้าที่มีรูป > 150px | หน้าที่เป็นตารางพร้อมรูปสินค้าเล็ก ๆ ถูกส่ง vision ทั้งที่ข้อความครบ | ใช้ vision เฉพาะรูปใหญ่/แผนภาพ/สแกน/ข้อความเสีย รูปในช่องตารางและเส้นขอบตารางไม่นับ |
| หน้าว่างทำให้ ingest "INCOMPLETE" ตลอด | PDF ใหม่มีหน้าว่าง (เช่นหน้า 6, 33) | หน้าว่างจริงไม่ใช่ความล้มเหลว |
| embed ทีละ chunk | 1 API call ต่อ chunk | batch (ค่าเริ่มต้น 24 ต่อ call, `EMBED_BATCH_SIZE`) ตรวจจำนวนเวกเตอร์ ถ้าไม่ตรงจะ fallback ทีละ chunk |
| vision ทีละหน้าต่อกัน | — | ขนาน `--workers` และใช้ cache ต่อหน้า (รันซ้ำไม่เสียโควตาหน้าที่สำเร็จแล้ว) |
| ตาราง vision เป็นข้อความก้อนเดียว | ขอบเขตแถวหาย | ขอให้ vision คืนตารางเป็น `columns` + `rows` แล้วใช้ตัวตัดตามแถวเดียวกับตารางเนทีฟ (cache แยกจากของเดิม) |

### สิ่งที่พบจากไฟล์จริง 4 ไฟล์ (2026-10-17) และแก้แล้ว

เทสต์สังเคราะห์ไม่เคยเจอปัญหาเหล่านี้ ต้องทดสอบกับไฟล์จริงเท่านั้น:

- `Table.extract()` ของ PyMuPDF ทำภาษาไทยเพี้ยน ("อุปกรณ์ในชุด" → "อปกรณ์ในุชด") จึงอ่านข้อความต่อ cell จากลำดับตัวอักษรในไฟล์โดยตรง
- คอลัมน์รูปภาพที่ว่างทุกแถวห้ามตัดระดับหน้า (ตารางหน้า 10 มี 9 คอลัมน์ หน้า 11–14 เหลือ 8 ต่อกันไม่ได้) ตัดเฉพาะคอลัมน์ที่ว่างทั้งตารางหลังต่อหน้าแล้ว
- ข้อความของแถวที่ล้นข้ามหน้า หรือค่าที่หลุดเป็นแถวแยก (เช่น ความจุ "50" ของ EASY 70 Plus) ถูกรวมกลับเข้าแถวเดิม แม้แต่หัวตารางที่ถูกตัดข้ามหน้า (ตาราง 2.4 มันสำปะหลัง) chunk จึงบันทึก `page_from`/`page_end` และ `verify_ingestion` นับหน้าตามช่วงนี้
- เซลล์รวมที่ยาว ("4: ธาตุอาหารรอง/เสริม คีเลต (EDTA Chelated) …คำอธิบาย…") ให้ชื่อสั้นเป็นคอลัมน์ `หัวข้อกลุ่ม` และเก็บคำอธิบายเต็มเป็นข้อความหนึ่งชิ้น (`table_note`) แทนการแปะซ้ำทุกแถว กลุ่มที่อยู่ท้ายหน้าก็ไม่หาย
- เลขหัวข้อที่แยกบรรทัดจากชื่อ ("3.1.2." + "ข้อกำหนดของระบบ") รวมเป็นหัวข้อเดียว ไม่ถูกตัวกรอง "เลขหน้าลอย" ทิ้ง
- บรรทัดที่ขึ้นใหม่เองต่อกับบรรทัดก่อนหน้าด้วยการเว้นวรรค ("20 ลิตร แนะนำ:") ส่วนบรรทัดที่ชนขอบแล้วตัดกลางคำจึงต่อติด ("ความจุถัง|พ่น")
- ตารางกว้าง (≥ 8 คอลัมน์) ไม่ถูกตัวกรอง "ตารางปลอม" ปัดตก แม้หน้าสุดท้ายเหลือแถวเดียวหรือข้อมูลบาง

Preflight ออฟไลน์บนไฟล์ใหม่ทั้ง 4: ตัวเลขทุกตัวในไฟล์อยู่ใน chunk ของหน้าเดียวกัน (0 จาก 1,539 ตัวหาย) ไม่มีหน้าที่มีข้อความแต่ไม่มี chunk

ลำดับ chunk ในหน้าเดียวกันถูกเก็บใน metadata `seq` และ `slide_retriever` เรียงตามนั้น (chunk เก่าไม่มี `seq` ลำดับจึงเหมือนเดิม)

## ข้อรับประกันที่คงไว้

- index ถูกแตะหลังจาก embed สำเร็จทุก chunk เท่านั้น upsert ก่อน แล้วลบ chunk เก่าที่ไม่ใช้แล้วทีหลัง
- หน้าที่ vision ล้มเหลวไม่ทับหน้าเดิมที่ดี สำหรับหน้าที่ยังไม่มีข้อมูล เก็บ native text ที่สะอาดพร้อม `extraction_complete=false`, `vision_status=unavailable` และรายงาน `native_only_pages` ทั้งไฟล์ยัง incomplete/exit 1 เพื่อ retry ภาพภายหลัง
- ไฟล์ PDF เปลี่ยนระหว่าง ingest → ไม่ publish
- เอกสารที่ถูกยกเว้นตาม source policy (UAV01, UA03, ขั้นตอนการยื่นขออนุญาต) ถูกปฏิเสธก่อนทำงาน
- chunk ทุกชิ้นมี `source_file`, `page_number`, `document_id`, `source_type` ตามที่ retrieval ใช้ ถ้าแถวหรือหัวตารางพิมพ์ต่อข้ามหน้า จะมี `page_from/page_end` และ citation แสดงช่วงหน้าจริงจาก metadata

## สถานะการตรวจสอบ

ผ่านแล้ว (ออฟไลน์): 53 เทสต์ใหม่ใน `tests/test_ingestion_v2_contract.py` (รวมการทำลายโค้ดโดยจงใจ 6 จุดแล้วเทสต์จับได้), เทสต์เดิมทั้งหมด (342 ผ่าน), `verify_ingestion` ผ่านบน index เดิม, schema ใหม่ของ vision ถูก Gemini SDK แปลงได้, dry-run บน PDF จริง 7 ไฟล์

**ยังไม่ได้ตรวจกับ API จริง** (เพราะโควตาเป็นคอขวดและยังไม่ได้รับอนุญาตให้เรียก):
1. prompt/ผลลัพธ์ vision แบบ `columns/rows` — โมเดลอาจคืนจำนวน cell ไม่เท่ากันหรือใส่หัวตารางผิดหน้า (ระบบเติม cell ว่างให้เท่ากัน แต่ไม่ตรวจความถูกต้องของค่า)
2. embedding แบบ batch กับ `gemini-embedding-2` — ถ้า API ตอบจำนวนเวกเตอร์ไม่ตรง ระบบ fallback ทีละ chunk (ถูกต้องแต่ช้ากว่า)
3. การปรับค่า vision ขนาน (`--workers`) กับ rate limit จริง — เริ่มที่ 3

ข้อจำกัดที่ทราบ: ตารางที่ไม่มีเส้นขอบ/เซลล์รวมซับซ้อนอาจถูก `find_tables` อ่านผิด; สไลด์ที่มีกราฟอาจถูกจับเป็นตารางปลอม (เมื่อใช้ vision ส่วนที่ vision ครอบคลุมแล้วจะถูกตัดซ้ำ); ตัวตรวจ `verify_ingestion` ตรวจหัวตารางและตัวเลขจากข้อความเนทีฟ ไม่ได้ตรวจความถูกต้องของค่าที่ vision อ่าน — ควรให้ผู้เชี่ยวชาญสุ่มตรวจหน้าสำคัญหลัง ingest
