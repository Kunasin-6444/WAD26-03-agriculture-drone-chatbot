# แผนต่อ: ingest ไฟล์ใหม่ให้ครบ และเทียบวิธี text / direct / ผสม

สถานะ ณ 2026-10-17 หยุดไว้เพราะ Gemini API ไม่เสถียร (504 หมดเวลาหลายครั้ง และ 429 ตอน embed) กลับมาทำต่อเมื่อโควตา/เซิร์ฟเวอร์ปกติ ไม่มีอะไรค้างที่ทำให้ระบบเสียหาย แต่มี **chunk ขยะ 12 ชิ้นใน index ที่ควรลบก่อน** (ข้อ 1)

## 1. สถานะ index ตอนนี้ (ตรวจแล้ว)

| ไฟล์ | chunks | สถานะ | ที่ต้องทำ |
| --- | --- | --- | --- |
| UAV06–UAV12 | 774 | legacy (ไม่แตะ) | — |
| ฟีเจอร์ผสมสาร.pdf | 74 | ครบ | — |
| ฟีเจอร์การลงทุน.pdf | 79 | ขาดหน้า 38 (vision หมดเวลา) ติดป้าย `missing:38` | รันซ้ำ |
| ฟีเจอร์วินิจฉัยโรคและ ปัจจัยเสี่ยง.pdf | 126 | **มี chunk ขยะ** หน้า 6 (×10) และหน้า 29 (×2) | ลบ + ingest ซ้ำ |
| ฟีเจอร์โดรนของฉัน.pdf | 9 | ขาดหน้า 2 (vision หมดเวลา) ยังไม่มีป้าย | `--force` |

**chunk ขยะ:** โมเดล vision ติดลูปซ้ำคำ ("standard standard standard …") บนหน้าตารางกว้างแล้วถูก publish เข้า index ถ้าไม่ลบ บอตอาจดึงข้อความนี้มาเป็นหลักฐาน วิธีลบ (ผมถูกระบบปฏิเสธสิทธิ์ตอนลองรัน จึงยังไม่ได้ลบ รอคุณอนุมัติหรือรันเอง):

```powershell
.venv/Scripts/python.exe -B - <<'EOF'
import chromadb, re
c = chromadb.PersistentClient(path="chroma_db").get_collection("drone_knowledge")
d = c.get(include=["documents","metadatas"])
loop = re.compile(r"\b(\w+)(?:\s+\1\b){7,}")
junk = [i for i,t,m in zip(d["ids"],d["documents"],d["metadatas"]) if m.get("source_sha256") and loop.search(t)]
print(len(junk), "junk chunks"); c.delete(ids=junk)
EOF
```

แล้วรัน `scripts.ingest ... --force` กับไฟล์ที่เกี่ยวข้อง (ข้อ 3) สำรองฐานข้อมูลก่อนเสมอ (`chroma_db` ~32MB; มีสำเนาก่อนทดลองอยู่ใน scratchpad ของเซสชันนี้ ซึ่งเป็นโฟลเดอร์ชั่วคราว)

## 2. ปัญหาที่ต้องแก้ในโค้ดก่อนรันต่อ

1. **กัน vision ลูปซ้ำ.** ผลที่มีคำเดียวซ้ำ ≥ 8 ครั้งติดกัน (หรือ element ที่ซ้ำกันเอง) ต้องถือว่าหน้านั้น degraded ไม่ publish เหมือนกรณี vision ล้มเหลว (เพิ่มเทสต์)
2. **ลดการเรียก vision ที่ไม่จำเป็น.** หน้าที่ถูกเลือกเพราะ `diagram_shapes_*` แต่จริง ๆ เป็นตารางที่อ่านได้จากข้อความในไฟล์แล้ว (วินิจฉัยโรค หน้า 6, 27, 29; โดรนของฉัน หน้า 2, 4; ผสมสาร หน้า 30) สร้างทั้งขยะและ 504 ควรไม่นับเส้นกรอบ/เส้นคั่นเป็นแผนภาพเมื่อหน้านั้นมีตารางเนทีฟที่รับแล้วและข้อความไฟล์ครบ
3. **ตั้งค่าเสถียรภาพ.** `VISION_TIMEOUT_SECONDS=90`, `--workers 2` (ค่าเริ่มต้น 30 วินาที / 3 ขนานทำให้ 504 บ่อย)
4. ทำแล้ว: ไฟล์ที่ ingest ไม่ครบจะติดป้าย `missing:<หน้า>` และการรันครั้งถัดไปจะ ingest ซ้ำเอง (vision/embedding ที่สำเร็จแล้วอยู่ใน cache จึงไม่เสียโควตาซ้ำ)

## 4. แผนเปรียบเทียบ text / direct / ผสม

**คำถามที่ตอบ:** วิธีไหนค้นเจอหน้าที่ถูกและให้หลักฐานที่มีค่าถูกต้องมากที่สุด เร็วและถูกที่สุด บนเอกสารใหม่ 4 ไฟล์ (≈124 หน้า)

**ขั้นตอน**
1. เขียนชุดคำถามอ้างอิง ~40 ข้อ (`tests/data/`) แต่ละข้อมี: คำถาม, หน้าที่ถูกต้อง, ข้อความที่ต้องปรากฏ (`must_contain`) ตรวจอัตโนมัติว่าข้อความนั้นอยู่ในหน้าที่ระบุจริง ส่วนข้อมูลที่อยู่ในรูปอย่างเดียวตรวจจากภาพหน้ากระดาษ แล้วให้ผู้เชี่ยวชาญตรวจรอบสุดท้าย
2. ingest แบบ direct ลงคอลเลกชันแยก `drone_pdf_pages_v1` (ฝัง PDF ทีละหน้า ≈124 calls ≈7 นาที) ด้วย `scripts.ingest_pdf <ไฟล์> <id> --mode direct`
3. สร้างคอลเลกชันชั่วคราวที่มีเฉพาะ 4 ไฟล์ใหม่ใน text index เพื่อให้เปรียบเทียบบนเอกสารชุดเดียวกัน
4. รันเทียบ 4 แบบ: (a) text dense อย่างเดียว (b) text hybrid (dense + BM25 แบบที่บอตใช้) (c) direct (d) ผสม text + direct ด้วย RRF
5. วัดต่อแบบ: hit@1/3/5/8 และ MRR ของหน้า, **ข้อความหลักฐานมีค่าที่ถูกต้องหรือไม่** (text: เนื้อหาที่เก็บ; direct: transcript ที่โมเดลอ่านตอนตอบ), เวลาต่อคำถาม, จำนวน API call ตอน ingest และตอนตอบ
6. รายงานเป็นตาราง พร้อมแยกกลุ่มคำถาม (ตาราง / ข้อความ / สูตร / ข้อมูลในรูป / พิมพ์ผิด)

**ไม่ได้วัดในรอบนี้ (ตั้งใจ):** คุณภาพคำตอบปลายทางจาก LLM เพราะโควตา LLM (KKU ~80–90 คำถาม/วัน) ไม่พอสำหรับ 40 ข้อ × หลายแบบ ให้ทำภายหลังกับแบบที่ชนะ

## 5. หมายเหตุ

- ผลวัดที่มีตอนนี้ยังไม่พอจะฟันธงว่าวิธีไหนดีที่สุด (ดูข้อสรุปในแชท: ข้อความในไฟล์แม่นสุดสำหรับหน้าที่มีข้อความ ส่วน retrieval ยังไม่มีข้อมูล)
- การทดลองแบบ direct ใช้โควตา embedding ราว 124 call แยกจาก LLM
- เอกสารใหม่เป็นสเปกฟีเจอร์ของแอปอื่น มีราคา อัตราสารเคมี และ system prompt ควรให้ผู้เชี่ยวชาญตรวจก่อนเปิดให้ลูกค้า
